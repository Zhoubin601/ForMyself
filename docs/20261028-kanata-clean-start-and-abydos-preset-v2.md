> 本文对 [技术设计 v1](20261027-kanata-technical-design-v1.md)、[P0 计划](plan.md) 中「旧温馨小家数据无损迁移、旧小暖默认实例」的要求作**局部覆盖**；其他有关加密、恢复、权限、世界隔离、用户确认后分阶段开发的约束继续有效。原始材料 raw/ 及历史记录保持不变。尚未确定的实现参数是建议，不能写成已确认事实。

## 2. 数据边界与全新模型

推荐继续以现有 chat 业务模块和注册 ID 为兼容入口，不建立一个能绕开密码、恢复协调器和备份参与者的平行系统。**业务格式可以全新设计，平台安全机制不能因此删除。**

关系：GlobalCharacterCard（卡版本及原始/标准化数据）→ CharacterInstance（worldId + 固定 cardVersion）；World → Conversation（private/group/character-to-character）→ Message（worldId、conversationId、senderType、senderId、turnId、batchId、实际时间）；另有 LorebookEntry、Memory、Relationship、WorldEvent、BackgroundTask、LifeGrant 和 WorldPreset（模板）。

关键不变量：

1. 同一原始卡可在不同世界实例化多次；角色实例、关系、记忆、情绪、世界事件不跨世界共享。
2. 群聊参与者必须属于当前世界；旧单角色 assistant 身份不得被复用为所有角色的真实发言者 ID。
3. 原始聊天默认不自动删除；记忆提取和摘要有来源与 revision；世界事件先校验、后按代码规则提交状态。
4. 模板数据与实例数据分开：模板更新不能覆盖世界已有聊天、关系、用户编辑及记忆。
5. 旧 chat v4 不做 v4→v5 内容迁移；但**新格式仍需严格版本入口、未来版本拒绝、读写错误门禁**。新聊天/单项备份/完整备份的版本号是候选，不能未经检查擅自共用一个常量。
6. 新持久化命名空间宜与旧 warm-home-v1 路径分离；是否分文件、分会话或数据库要依据 P2 性能与安全验证确定，不宣称现有 JSON 已支持真分页。

## 3. 阿拜多斯五人预设的交付规格

**预设 ID 建议：** builtin.abydos-taskforce.v1（标识符为工程建议，创建后需稳定不变）。

| 角色预设 | 初始化要求 |
| --- | --- |
| 小鸟游星野 | 独立卡定义、阿拜多斯世界实例、人格核心与说话习惯、初始关系关联 |
| 砂狼白子 | 独立卡定义、阿拜多斯世界实例、人格核心与说话习惯、初始关系关联 |
| 十六夜野宫 | 同上 |
| 黑见芹香 | 同上 |
| 奥空绫音 | 同上 |

**完整预设包**应至少包含：manifest（ID/版本/来源/兼容 schema）、world（名称/规则/默认对话模式/时间基准）、五份 cards（可审查的原创摘要性角色设定）、五个 characterInstances 的模板定义、世界书及角色专属知识条目、初始人物间关系、一个五人群聊、五条用户与角色的独立私聊会话及默认设置。未来的用户自定义预设导入须经过单独格式/安全审查。

初始化规则：

1. 首次启用彼方时展示**全新初始化与旧数据永久删除确认**，确认完成后从预设包建立世界；失败要保持可重试状态，不能将读/写失败解释成「已初始化的空世界」。
2. 预设种子创建须用稳定模板来源标识与初始化事务/检查点去重。重复进入、应用中断恢复、重试不能复制五份角色或重复建群。
3. 五个角色都拥有各自私聊入口，群聊包含五个角色，但**初始化时没有伪造的既往对话、约会、重大事件或用户私人记忆**。初始关系仅表示预设世界设定，之后由真实互动逐步发展。
4. 首次使用立即可以进行文字私聊和五人群聊；聊天生成沿用全局 DeepSeek。未配置 API Key 时可浏览预设，但不能伪装为回复成功。
5. 自主世界开关、主动联系和 Android 通知彼此独立；默认开启状态、每日场次和 quiet hours 仍以最终设置决策为准。工程建议初次启动前不自动发起可能计费的 AI 任务。
6. 禁止将角色或世界固定写死进业务 Store：预设是可版本化的独立数据输入，普通世界也走同一实体创建接口。
7. 导入预设/卡片仅读取明确授权文件，不执行卡附带脚本或远程链接；保留安全未知扩展字段。世界书注入须检查知情范围和生活权限。
8. 预设角色设定以独立撰写的摘要为主；不擅自打包官方头像、立绘、音乐、完整角色台词或第三方角色卡内容。暂用原创通用占位图/文字头像，允许用户导入自行有权使用的角色卡与图片。发布前另做素材与版权审查。
9. 预设与官方设定的准确性（姓名、成员、关系、背景）应由后续内容审核核对；本方案不把角色详细 lore 当作已经验证的原作事实。

## 4. 旧温馨小家：永久清理而不是迁移

**不能把“Git 分支独立”等同于“手机的数据独立”**：Android 应用 ID、数据目录和 Preferences 可能仍然共享。这里的 D01 是未来产品运行时清理规则，**不是此次在 GitHub 上删除任何文件的授权**。

旧数据清理范围应由 P2 对实际实现逐项列清，至少检查：

- chatStorage 内旧加密主文件 warm-home-v1.enc、临时文件 warm-home-v1.tmp、备份文件 warm-home-v1.bak，及其他经源码核实的旧专属副本/缓存；
- chatPersistence 使用的旧恢复键 my_chat_recovery_encrypted_v1 和关联的旧聊天专用状态；
- 旧主动/延迟消息队列与属旧温馨小家的 Android 本地通知、通知频道、触发 ID；
- 旧聊天在完整/单项备份中的分派及恢复入口，不使旧聊天从备份悄悄复活。

**必须明确排除：** 主密码和认证配置、全局 DeepSeek Key 和配置、其他生活模块的数据文件、其他模块通知、完整恢复协调器及恢复日志（即使其中出现 chat 内容，也不可直接删除或越过运行中恢复任务）。

建议受控操作顺序：

1. P2 在合成设备/隔离测试环境中完成旧文件与依赖枚举，检查受保护会话/改密/恢复操作是否忙碌，禁止与仍在写旧数据的 watch/定时器并发。
2. 在真正启用新彼方的设备端显示明确警告：旧聊天、记忆、关系、事件将不可恢复；外部手动导出的备份文件不在应用可清理范围内；由用户在界面确认。
3. 先暂停旧任务、停止通知并锁定旧聊天写入，在受保护操作租约内确保没有未结束的保存/恢复；**失败则中止，不执行部分清理**。
4. 按幂等的清理清单删除旧模块专属的文件/键/队列，记录**非敏感的清理阶段状态**，逐项核实不存在；不得为了“完成”而把错误当作文件不存在。部分操作完成后遇故障，重试只能继续补齐，绝不恢复旧数据到新模型。
5. 完成清理后才提交新世界初始化完成标记；旧聊天入口永久停用，业务读路径不应回退到旧文件。新存储首写与标记采用可恢复顺序，处理中断不复制预设、不写入空数据覆盖已有新数据。
6. 与新系统兼容的旧版本 App 回退策略需明确：旧版可能重新建立 warm-home 文件；不提供“旧版回退仍安全”的未经验证承诺。

关于**备份导入**：

- 旧单项温馨小家备份：在新彼方入口显式拒绝，不迁移/静默导入，说明此备份格式已停用。
- 旧完整备份（v1–v12）：继续保证其中**非聊天模块**可受控恢复；检测 legacy chat 时做预览和明确确认，忽略/剔除旧聊天部分，避免随后覆写或激活旧数据。若当前恢复协调器不能实现安全的部分恢复，就在 P2 完成专门的受检兼容适配前禁止这一路径，不得以“已兼容”宣告。
- 彼方新备份：完整导出五人卡/模板来源、世界、实例、私聊群聊、消息、世界书、记忆、关系、事件、授权和必要任务状态；不包含旧温馨小家数据，也不使 API Key 进入卡片/日志/统计。
- 应用无法自动删除用户自行保存于其他位置的旧 JSON 备份；需要 UI 告知用户自行处理，不能声称已经全域删除。

## 7. 新增专项验收

1. 设备上已有旧 warm-home 加密数据：首次进入只展示删除警告，不静默删除；明确确认后原旧主/临时/备份文件和旧恢复键全部移除。
2. 仅当文件确实不存在时才视为成功；权限不足、解密/加载失败、恢复进行中、删除中断都不被当作“正常空世界”。
3. 重复初始化三次，均只有**五角色实例、五私聊、一个五人群聊**，没有重复创建和意外 AI 调用。
4. 每个角色都有不同 ID；群聊成员 ID 全属于阿拜多斯世界；其他世界实例不能被访问。
5. 不存在旧小暖/旧聊天/旧记忆被加入提示词、索引、备份或 UI；默认预设无伪造的已发生聊天记录。
6. 恢复 v1–v12 全备的非聊天模块时，不丢失它们，也不复活旧聊天；旧单项 chat 备份得到明确不支持反馈。
7. 清理旧聊天不影响其他模块、全局 API 配置、主密码及恢复协调器；应用中断重试不会误删新彼方的数据。
8. 同一角色卡在新世界再次实例化时不共享记忆；世界书检索通过范围/权限测试。
9. Android/Web 的通知、加密、备份、恢复与数据体量验证分别提供真实执行证据；目前全部属于待测项。
