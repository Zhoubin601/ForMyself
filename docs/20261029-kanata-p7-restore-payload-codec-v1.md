# P7 大型恢复日志的数据包装设计

背景：生产Chrome实际完整恢复测试，100k合成消息导入峰值约2GB，含恢复前后两张完整图的恢复超过180秒；冻结768MiB/120秒门槛未通过。重复副本已减少，但不能用只测Store或磁盘分页绕过实际恢复协调器及其自包含回滚日志。数据量较小时保持现有路径。

## 不改变密码协议和协调器

外层仍原 `version:1 / salt / iv / ciphertext`，相同16字节盐、PBKDF2-SHA256 210000次、AES-256-GCM与12字节IV、Base64。路径、主/临时/提交标记、验证读回、SHA256、probe/commit/clear及恢复写保护均不改变。没有新增数据库、明文日志或直接apply入口。

新增的是**加密内部JSON载荷的数据包装**。小于256KiB的记录仍为原 `{version:1,previous,target}`。更大记录序列化为有界UTF8块，经gzip后形成：

```json
{"type":"formyself-restore-payload","version":2,"encoding":"gzip-json-v1","plainBytes":1234567,"data":"<gzip Base64>"}
```

该包装整体在原AES-GCM内认证加密；编码类型与声明长度同样被认证。`openRestoreRecord` 验证/解密后解包，再返回原始记录给原协调器验证与恢复。v1历史日志直接兼容读取；已有日志只读，不在probe/读取时迁移或删除。旧应用打开新载荷会得到version2，原协调器必须在业务写入前拒绝并保留门禁；不伪装为旧记录后让其错误恢复。

完整对外备份仍原v13/单项v1，不把gzip载荷、磁盘引用或新日志类型交给旧完整备份normalizer；旧v1–v12非聊天数据恢复/明确丢弃旧聊天不变。

## 有界性和失败顺序

流式序列化只接受惰性JSON DTO，拒绝getter、symbol、稀疏数组、循环、非有限数和运行时对象，不调用外部toJSON；保持对象键序与JSON转义、UTF8代理对边界。已验证canonical DTO在prepare时为私有副本，不能被UI修改。

工程安全上限为解压后256MiB；压缩流读取时逐块计数，超限在日志写入与业务apply前失败。解包只在AES-GCM认证成功后进行，逐块核对被认证的plainBytes与上限，UTF8和JSON解析失败只返回稳定错误，不回显原文。未知载荷版本/编码、无解压能力、坏gzip、错密码、篡改、长度错误均保留已有日志/写保护，不以空记录替代。

测试环境使用Node24/实际Chrome及目标Android WebView的CompressionStream/DecompressionStream；生产能力缺失应明确失败，不改成明文或关闭验证。该上限不是AI消费限额，不截断用户数据；超过上限需明确报错而非部分恢复。

## 验证要求

新增载荷单元测试：JSON字节/Unicode等价、大小阈值与v1兼容、认证后才解压、声明长度/上限、未知版本/编码、坏gzip/错密/篡改、隐私错误。实际协调器补大载荷参与者失败回滚、保留日志重开恢复，以及旧v1–v12矩阵回归。完整check后再建立不可变生产Web样本与Android候选，重新测1k/10k/100k，不能把本设计当通过报告。

风险：不支持旧应用完成新载荷恢复（会明确拒绝而非错写）；极大低可压缩资料或大量来源全量保留仍可能触及内存/上限，必须实测并报告。P7仍No-Go，未以压缩成功取代全链路验收。
