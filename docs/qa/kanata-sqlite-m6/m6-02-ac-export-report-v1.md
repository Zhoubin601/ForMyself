### 2.2 负向拒绝验证（API 30 & API 34 均 PASS）

- 源库 Schema `user_version=4`：`UNSUPPORTED_FORMAT` 拒绝。
- `event_array_order` 缺失 ordinal / 空洞 ordinal (`0 -> 2`)：`ARRAY_ORDER_INCOMPLETE` 拒绝，绝不自动修复。

## 4. A1 / A2 / C 双平台性能与资源汇总（口径修正版，Cold + 5x Warm Median [Min–Max]）

> 测量口径说明（已按独立审计要求全面修正）：
> - **轮换策略**：每种规模均先做 `1` 次冷测 (`A1 → A2 → C`)，再进行 `5` 次交错轮换热测：`{A1,C,A2}` → `{C,A2,A1}` → `{A2,A1,C}` → `{A1,A2,C}` → `{C,A1,A2}`。
> - **写入阻塞 (`writeBlockMs`)**：C 与 A2 均从调用 `beginSnapshotFreezeAndDrain()` **之前**开始计时至 `endSnapshotFreeze()` 结束；A1 全周期持锁，故 `writeBlockMs = exportExecMs`。
> - **禁止重复计时 & 不可适用阶段标 `N/A`**：A1 `sqlcipher_export` 内联读库/KDF/页加密/写文件，不再把开库耗时充当 `snapshotPinMs` 或将同一段时间重复记入 DB Read 与 Spool Write（仅记录 `exportExecMs` 与 `fsyncReadbackMs`）；A2 明确标 `snapshotPinMs = N/A`、`dbReadMs = N/A`，仅单独记录 `freezeDrainMs`、`checkpointCloseMs`、`fileCopyMs`、`kdfAeadMs`（`changePassword` rekey）与 `fsyncReadbackMs`。
> - **A2 严格离线合同**：A2 每轮使用**独立合成活跃 WAL 副本**，按顺序执行：`freeze -> drain -> wal_checkpoint(TRUNCATE) -> 关闭全部源连接 -> 校验 -wal/-shm 消失 -> 复制稳定文件 -> endFreeze -> changePassword rekey`。
> - **统一高频资源采样 (`ResourceSampler`)**：A1 / A2 / C 统一采用 `10 ms` 周期采样 `/proc/self/statm` (`VmRSS`)、`Debug.getNativeHeapAllocatedSize()`、Java 堆、`walPeakBytes` 与 `spoolPeakBytes`。

## 5. 定量分析与选型结论（修订版）

1. **写入阻塞稳定性**：修正从 `beginSnapshotFreezeAndDrain()` 前起算后，Scheme C 在 `1k / 10k / 100k` 下的 `writeBlockMs` 中位数稳定在 **`11–12 ms`** (API 34) / **`5–6 ms`** (API 30)，不随数据量膨胀；A1 `sqlcipher_export` 阻塞写入达 `3,343–4,425 ms` (API 34) / `1,242–2,424 ms` (API 30)；严格离线合同下 A2 冻结停写并强制关连达 `48–434 ms` (API 34) / `20–170 ms` (API 30)。
2. **同范围对比澄清（排除语义范围差异混淆）**：A1/A2 原包包含 3 张运行表且未投影任务状态；为验证纯粹格式与页对齐压缩效率，新增 `measureSameScopeSizeComparison`（与 C 完全同范围的 50 表 + 投影后基准库再经 `sqlcipher_export` 导出）：
   - **1k**：同范围 A1 **`1,245,184 B`** vs Scheme C **`197,584 B`**（仅为 A1 的 `15.9%`）。
   - **10k**：同范围 A1 **`4,259,840 B`** vs Scheme C **`1,943,106 B`**（仅为 A1 的 `45.6%`）。
   这证明 Scheme C 的体积优势主要来自紧凑二进制流与消除 SQLite 4 KiB 页对齐空间浪费，而非仅依赖删表过滤。
3. **取消响应真实性对比**：
   - **Scheme C**：全阶段协同支持取消，API 34 实测 **`5 / 11 / 7 ms`**，API 30 实测 **`3 / 7 / 62 ms`**。
   - **A1**：`rawQuery("SELECT sqlcipher_export(...)", null, CancellationSignal)` 可触发底层中断（API 34/30 实测 `A1_midExportCancelSupported=true`，`A1_waitAfterCancelMs=0 ms`），但一旦触发需直接丢弃未完成目标库。
   - **A2**：文件复制阶段支持协同取消（`A2_fileCopyCancelSupported=true`；API 30 10k 下因 6.8 MB WAL 未先触发/主库 4 KB 已完成返回 `false`），而 **`PRAGMA changePassword` / rekey 不支持安全中途取消 (`A2_rekeyCancelSupported=false`)**。
4. **内存红线安全**：统一 10 ms 采样下 100k 规模三路线 Peak RSS 为 `184.0–190.3 MiB` (API 34) / `214.8–217.3 MiB` (API 30)，Peak Native Heap 约 `105.7–106.0 MiB`，Java Heap `6.2–13.0 MiB`，均远低于 `512 MiB` 红线。
5. **100k 下 CPU 耗时权衡**：Scheme C 在 `100k` 规模总耗时中位 `69.8s` (API 34) / `31.0s` (API 30)，主要来自 `dbReadMs` (`64.4s` / `26.3s`) 与高频 `10 ms` 采样器运行；作为可随时 `5–62 ms` 中断且仅阻塞写 `5–12 ms` 的后台任务可接受，后续产品化可通过原生游标批读进一步优化。
