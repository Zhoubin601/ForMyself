## 1. 候选路线定义与适用边界（严禁混淆前提条件）

| 路线 | 技术实现 | 一致性模型与并发写入约束 | 产物形式与格式契约 | 适用定位 |
| --- | --- | --- | --- | --- |

## 2. 跨端互操作性与 Schema 005 目标恢复验证（API 30 与 API 34 均 PASS）

### 2.1 Node / WebCrypto ↔ Android Native 逐字节互操作

1. **空包向量 `vectors-v1.json` 逐字节对拍**：
   - Android Scheme C 对空 Schema 005 SQLCipher 数据库（含 `schema_migrations`/`schema_migration_applications` 运行表）导出结果：`2,874 B`，SHA-256 `1aff9f0016b0411657b86cb338c3a768929b71cc3f379a6095af7f2e71cfb17c`，`transcriptHex` = `e412add3d03fc4334d07e5b1e07d0bbb3726180f1a5004edb9c61dc6fda1b74c`，50 个 `Verifier`（45 业务 + 5 派生）与 `vectors-v1.json` **逐字节完全一致**。
   - 同时确认运行表自动被排除（导入恢复至隔离目标后 `schema_migrations=0`, `schema_migration_applications=0`）。
2. **有数据合成库互操作 `node_interop_populated.kpb1`**：
   - 使用 [buildNodeInteropFixture.mjs](portable/buildNodeInteropFixture.mjs) 生成含中文、emoji 补充平面、NFD (`e\u0301`)、嵌入 NUL (`\u0000`)、前导 `\ufeff` BOM、`-0.0`、`background_tasks`、`world_events`/`world_effects`/`effect_baselines` (`ordinal`) 的参考容器（`4,292 B`，SHA-256 `e2c53f578a5bb5e60f949b7983eefab11becb6433604ca73a8f75af30ce61dcb`）。
   - Android Native Scheme C 在相同合成材料下导出结果同为 **`4,292 B`**，SHA-256 **`e2c53f578a5bb5e60f949b7983eefab11becb6433604ca73a8f75af30ce61dcb`**，与 Node 参考产物**100% 逐字节相等**。
   - 从 `node_interop_populated.kpb1` 与 Android 随机密钥导出包双双恢复至全新 Schema 005 SQLCipher 目标库后，验证：`user_version=5`、`application_id=1263424577`、`integrity_check=ok`、`world_identities.display_name` UTF-8 原始字节精确相等（完整保留前导 `\ufeff` 与内嵌 `\u0000`）、`background_tasks` 经 `pause-sending-v1` 投影（`proactive/running -> cancelled, lease_until=0`）、3 张运行表为 `0` 行。
3. **Android 随机导出 → 宿主机 Node 反向解码验证**：
   - 从 Android 模拟器拉取 `m6_android_to_node_interop.kpb1`（`4,292 B`, SHA-256 `cbf0b025076d538baaaa973b56020932b5b34aa96effca38c0c94ee3b9ba8f38`）及 `m6_bench_1000_sample.kpb1`（`197,584 B`, `3` 个 DATA 帧, SHA-256 `f5a1203ddd6359e0b6c2ea06b119ee72136783501cf25cd6ef6b494cf5c12ed2`），使用宿主机 `node` + [syntheticCodec.mjs](portable/syntheticCodec.mjs) 解码进隔离 `node:sqlite` Schema 005 目标库，50 表 verifier 全部匹配，恢复精确 `1,000` 条消息与 `pause-sending-v1` 任务状态（`task-1: cancelled`, `task-2: cancelled`, `task-3: pending`, `lease_until=0`）。

> [!NOTE]
> **跨端实测发现**：
> 1. Node v24.14.1 实验性 `node:sqlite` 模块在读取 `TEXT` 列时会于嵌入 `0x00` 字节截断（实测 `SELECT display_name` 将 12 字节截断为 7 字节）；而 Android `KanataM6BoundedRowReader` 基于 `CAST(col AS BLOB)` + 严格 RFC 3629 解码无此截断，已在 [buildNodeInteropFixture.mjs](portable/buildNodeInteropFixture.mjs) 对齐完整 UTF-8 基准。
> 2. SQLite B-tree 对浮点值 `-0.0` 存储规范化为数值 `0`（Node 与 Android 表现一致），双向线编码一致且恢复数值为 `0.0d`。

### 2.2 负向拒绝验证（API 30 & API 34 均 PASS）

- 源库 Schema `user_version=4`：`UNSUPPORTED_FORMAT` 拒绝。
- `event_array_order` 缺失 ordinal / 空洞 ordinal (`0 -> 2`)：`ARRAY_ORDER_INCOMPLETE` 拒绝，绝不自动修复。
- 导入 `0x0001` 生产 profile、损坏 magic：在 KDF 前 `0–3 ms` 内拒绝 (`UNSUPPORTED_FORMAT`)。
- 错误密码：`AUTH_FAILED` 拒绝。
- 篡改 DATA/Footer 密文或 Tag：`AUTH_FAILED` 拒绝；Footer 后追加 1 字节：`INVALID_CONTAINER` (`trailing-bytes`) 拒绝；失败时不留任何目标 DB 文件。

> - **轮换策略**：每种规模均先做 `1` 次冷测 (`A1 → A2 → C`)，再进行 `5` 次交错轮换顺序热测：`{A1,C,A2}` → `{C,A2,A1}` → `{A2,A1,C}` → `{A1,A2,C}` → `{C,A1,A2}`。

## 5. 定量分析与选型结论

1. **写入阻塞稳定性**：Scheme C 在 `1k`、`10k`、`100k` 下的写阻塞时间恒定为 **`4–5 ms`**（仅用于排空写入门禁并执行 `DEFERRED` 事务首条 `SELECT` 固定 WAL 快照），不受数据量或后续 KDF/IO 影响；A1 则随数据导出增长且阻塞可达 `1.9s+`；A2 需要离线停写并关闭全部业务连接。
2. **输出体积优势**：Scheme C 通过紧凑二进制 `kanata-logical-v1` + 排除 3 张运行表及 SQLite B-tree 页对齐开销，产物体积在 `1k` 仅 `197.6 KiB`（A1 的 **`15.9%`**）、`10k` 仅 `1.94 MB`（**`45.6%`**）、`100k` 仅 `19.76 MB`（**`55.4%`**），直接缩减移动端的存储峰值与传输带宽。
3. **内存红线安全**：在 100k 消息 + 58.3 MB 活跃 WAL 下，Scheme C 峰值 RSS 为 `175.3 MiB` (API 34) / `198.2 MiB` (API 30, `203,004 KiB`)，Java Heap 控制在 `6.4–10.4 MB`，**远低于 Android 512 MiB 红线**。
4. **诚实记录 C 路线的 CPU 耗时权衡**：在 `100k` 规模下，Scheme C 总耗时达到 `26.9s` (API 34) / `22.7s` (API 30)，瓶颈 `~91–95%` 集中在 `dbReadMs`（Java/JNI 逐行游标与每行 `JSONTokener` 校验 `extensions_json` 约 60 万字段读取；100k 消息下 Native Heap 增长到 `77 MB` 主因亦是 SQLCipher 页缓存与 CursorWindow 批次切换）。尽管 `22–27s` 属于纯后台可取消流式任务且写阻塞仍仅为 `4 ms`，但后续若进入产品化优化，值得评估原生 JNI 单行序列化或减少非必需 `JSONTokener` 重复对象分配，进一步缩短 100k 导出时长。
