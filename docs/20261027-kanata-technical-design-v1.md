# 彼方 · Kanata 技术设计 v1
## 一、先确定整体架构
我建议保留 ForMyself 现有的 Vue 3、Pinia、Capacitor 和 DeepSeek 调用链，在原有应用中逐步扩展，而不是另外搭一套后端。
**交互层**
私聊 · 群聊 · 角色卡 · 世界书 · 生活日程


**应用服务层**
对话与发言决策


记忆与上下文


生活与主动互动


世界事件与恢复


**数据与平台层**
现有加密存储 · 消息与事件索引 · 任务队列 · 备份恢复


**AI 能力层**
统一 AI 客户端 · DeepSeek · Token 统计 · 超时与失败处理


这里有个关键原则：AI 负责理解、判断和生成，应用代码负责数据一致性、权限、任务状态和持久化。

例如，AI 可以建议“星野今天与白子发生了一次争执”，但不能仅凭生成了一段文字，就直接修改两个人的全部关系数据。事件必须经过校验、保存，并按确定的规则更新状态。
## 二、先看现有代码：有几个关键问题必须提前处理
我已经继续检查了 ForMyself 的实际源码。这里有些好消息：我们不需要从零开始；但也有几个地方不能直接拿来当作多角色系统的基础。
现有聊天模块已经具备不少基础能力

包括记忆提取、行为规划、每日状态、关系更新、角色自我变化候选、主动消息和延迟补话。应当在这些功能上扩展，而不是另写一套与它们冲突的系统。

源码：chatRealism.js、chatRelationship.js


现有消息没有独立的发言者身份和会话归属

目前消息角色主要区分 user 和 assistant。要支持多个角色发言，需要新增 senderId、conversationId 和 worldId 等字段，而不是只改头像与名称。

源码：chatRecords.js


现有 socialCast 和 virtualEvents 不适合直接承担新职责

socialCast 目前最多保留三个角色；virtualEvents 的规范化还会按日期归并事件。因此，它们不能直接充当完整的角色档案库和世界事件账本。


现有加密存储和恢复机制必须保留

聊天数据目前使用加密文件、临时文件、备份文件以及加密恢复副本。新功能必须接入现有保存、恢复和主密码生命周期，不能另建一条绕过保护的写入路径。

源码：chatStorage.js、chatPersistence.js


这些结论决定了：我们应该升级现有聊天领域模型，而不是新建一个与现有聊天数据互不相通的平行系统。
## 三、彼方的数据模型怎么设计？
先定义逻辑模型。具体采用几个 JSON 文件、是否拆分存储，是后续实现时的决定；不能把逻辑模型直接等同于某种物理存储方案。
### 3.1 世界与角色
| 实体 | 核心字段 | 解决的问题 |
| --- | --- | --- |
| World | id、name、rules、lastSimulatedAt | 世界独立运行、时间推进 |
| CharacterCard | id、format、rawData、normalizedData | 保存导入的角色原始设定及解析结果 |
| CharacterInstance | id、worldId、cardId、state | 角色在特定世界中的独立状态 |
| LorebookEntry | id、scope、keys、content、priority | 管理世界书及角色专属知识 |

这里最重要的是区分 角色卡和角色实例。

例如，同一张小鸟游星野角色卡，可以在两个世界中各创建一个角色实例：


世界 A：阿拜多斯

记忆、关系、活动安排和事件历史独立保存。


世界 B：原创校园

使用同一角色设定，但拥有另一套独立状态。


上图只是示意，不代表实际导入的角色卡或最终 UI。

如果两边共用同一个 CharacterInstance，就可能出现世界 A 发生的争执影响世界 B 的关系，或者一个世界的聊天记忆泄露到另一个世界。

所以：
- 角色卡保存相对稳定的人格与背景。
- 角色实例保存特定世界中的状态。
- 记忆和关系必须有明确的世界归属。
- 角色卡被修改时，不应自动覆盖已经形成的角色经历。
### 3.2 会话与消息
| 实体 | 核心字段 |
| --- | --- |
| Conversation | id、worldId、type、participantIds |
| Message | id、worldId、conversationId、role、senderId、content、createdAt |

其中 Conversation.type 至少支持：
- private：用户与一个角色私聊。
- group：用户与多个角色群聊。
- 后续可以扩展角色间自主交流，但不必第一版就提供独立的聊天界面。
消息需要同时区分模型角色与真实发言者。例如：
```json
{
  id: "msg-001",
  worldId: "world-abydos",
  conversationId: "conv-001",
  role: "assistant",
  senderType: "character",
  senderId: "character-hoshino",
  senderNameSnapshot: "小鸟游星野",
  content: "嗯……老师今天看起来有点累呢。",
  createdAt: 1793100000000
}
```


role 仍然保留现有 user / assistant 语义，尽量减少与旧聊天代码的冲突；senderId 才负责识别实际说话的角色。

senderNameSnapshot 用于保留历史消息当时显示的名称，避免以后改名导致旧聊天的显示语义发生变化。
### 3.3 记忆、关系与世界事件
这三个模块必须分开。
| 实体 | 核心设计 |
| --- | --- |
| Memory | ownerType、ownerId、worldId、sourceMessageIds、status |
| Relationship | worldId、fromId、toId、关系维度、来源事件 |
| WorldEvent | worldId、participants、sourceMessageIds、causedByEventIds、effects、status |

记忆不再只是一段文本，而是一条可以追溯的事实记录。

例如：
记忆：星野答应白子周五一起训练
来源：消息 M102、M106
所属世界：阿拜多斯
所属角色：星野
状态：有效


如果 M106 后来被修正，系统可以检查相关记忆是否仍然成立。

世界事件则更进一步：
事件 E01：白子与星野约定训练
    ↓
事件 E02：星野因临时事务迟到
    ↓
事件 E03：白子表达不满
    ↓
关系状态发生变化


这里不是让 AI 直接写入最终关系数值。

而是先生成事件候选，校验来源与参与者，再由应用代码按照确定的规则提交状态变化。

如果事件被撤销，还要能找到它影响过哪些状态，并判断哪些后续事件需要重新评估。

注意：撤销事件不能简单地把关系数值恢复到旧值。 如果之后又发生了其他互动，直接回滚旧数值就会覆盖新的变化。因此必须保留事件与状态更新之间的关联。

## 四、数据迁移：不能丢掉现有的小暖聊天记录
这是整个设计里最需要谨慎处理的部分。

当前聊天数据版本是 4，聊天备份版本也是 4。完整备份系统另有自己的版本体系，现有架构说明要求继续兼容完整备份 v1–v12。

我建议把新数据格式作为一次明确的版本迁移，而不是直接改写旧字段的含义。
从旧数据迁移到新模型
**旧聊天数据 v4**

小暖、聊天消息、记忆、关系状态、每日事件摘要


**迁移与验证**
1. 创建一个默认世界。
2. 把小暖映射为默认角色实例。
3. 创建默认私聊会话。
4. 给旧消息补充世界、会话和发言者标识。
5. 把旧记忆映射到新记忆归属模型。
6. 保留旧事件摘要，不凭空补造事件因果。
7. 验证数量、标识、内容和时间戳。


**新数据模型 v5**

旧聊天可继续使用，新功能逐步接入


迁移必须满足四个要求：
1. 幂等性： 同一份 v4 数据重复迁移，不会重复创建角色、会话和消息。
2. 失败保护： 迁移或验证失败时，不得把旧数据当作空数据覆盖。
3. 备份兼容： 旧备份仍可导入，新备份能够正确恢复所有新实体。
4. 安全兼容： 继续使用现有加密保存、恢复日志和受保护会话流程。
这里还有一个容易遗漏的细节：现有 virtualEvents 是按日期整理的摘要，不能把它们当作已经具备完整证据链的事件账本。迁移时应标记为旧摘要，不能伪造原始消息引用。
## 五、存储方案：先不急着引入 SQLite
现有聊天数据主要保存在一个加密 JSON 文件中，并通过临时文件、备份文件和加密恢复副本保障写入恢复。

如果现在直接改成 SQLite、重新设计所有备份和主密码逻辑，工作量会明显增加，风险也会扩大。

我建议分两步。

第一阶段：
- 暂时沿用现有加密存储与恢复机制。
- 抽象出统一的数据访问接口。
- 为多世界数据增加规范化和校验。
- 使用合成数据测试消息数量增加后的读取、加密和保存耗时。
第二阶段：

如果规模测试表明单一 JSON 快照已经无法满足要求，再单独设计持久化迁移，评估分世界存储、加密数据库或其他方案。

这不是说 JSON 一定够用，而是不能在没有性能数据的情况下，贸然同时更改业务架构与安全存储。

## 六、AI Agent 分阶段开发计划
下面这套计划是为了让 Agent 每完成一阶段，都能独立验证，不需要等整个项目写完才发现架构错误。
### P0 — 需求冻结与架构基线

需求冻结与架构基线
当前已完成部分静态审查
阅读 AGENTS.md、架构接口说明书及现有聊天代码；检查当前 Git 状态；整理数据模型、迁移策略和验收标准。

**验收：** 划与实际源码一致，没有擅自修改代码，也没有覆盖工作区现有改动。


### P1 — 纯数据模型与迁移测试

纯数据模型与迁移测试

新建角色、世界、会话、记忆和事件的规范化逻辑。先使用合成数据测试，不改 UI，不接真实 AI。

**验收：** 世界数据隔离、稳定 ID、非法数据拒绝、旧数据映射正确。


### P2 — 存储与备份兼容

存储与备份兼容

接入现有聊天 Store、持久化队列和备份注册器；升级聊天数据及备份格式，建立显式迁移。

**验收：** 备份导入、加密读写、强制中断恢复、重加密及恢复失败保护。


### P3 — 角色卡与世界书

角色卡与世界书

优先支持常见 PNG / JSON 角色卡，保留原始元数据；建立角色库、世界库和关键词世界书检索。

**验收：** 式验证、字段保留、导入导出往返、世界书预算与角色知识边界。


### P4 — 多世界私聊与群聊

多世界私聊与群聊

增加会话选择、发言者身份、角色参与判断和群聊 UI；优先响应明确的 @，其他角色按规则决定是否发言。

**验收：** 换世界不串消息，角色不会重复发言，旧私聊仍然正常。


### P5 — 长期记忆与事件账本

长期记忆与事件账本

引入记忆来源追溯、冲突更新、事件提交、状态影响记录和撤销机制。

**验收：** 复任务不重复写入；来源修改后能识别失效记忆；事件撤销不会覆盖后续状态。


### P6 — 虚拟生活与离线恢复

虚拟生活与离线恢复

让角色拥有日程、情绪、关系变化和主动互动；应用恢复运行后，按规则补算遗漏的状态变化。

**验收：** 复打开不重复生成事件；错过的通知不会全部补发；补算不会把虚拟经历冒充真实经历。


### P7 — 安全、性能与交付

安全、性能与交付

完成敏感会话、数据增长、备份恢复、Android 实机或隔离模拟器验证。

**验收：** 规质量命令全部通过，原有功能无回归，所有未覆盖项如实记录。


每个阶段都要先有可验证的完成条件，再进入下一阶段。不能让 Agent 一次性生成几十个类，然后用“构建成功”代替功能验收。

### 四、目标领域模型

必须明确区分：
- World：世界。
- CharacterCard：角色原始设定及标准化定义。
- CharacterInstance：角色在特定世界中的独立状态。
- Conversation：私聊或群聊。
- Message：消息及其真实发言者。
- Memory：具有世界归属和来源引用的长期记忆。
- Relationship：角色之间的独立关系状态。
- LorebookEntry：按世界或角色范围激活的设定条目。
- WorldEvent：可追溯、可验证、可撤销的世界事件。
- BackgroundTask：可以持久化、去重、恢复的后台任务。

同一张角色卡在不同世界中的角色实例必须相互隔离。
不得把旧 virtualEvents 直接当作完整事件账本。
不得让 AI 生成的候选事件绕过验证直接修改正式状态。

### 五、数据安全

- 旧聊天、记忆、角色状态和备份必须兼容。
- 迁移必须幂等，失败时不能写入空数据覆盖原始数据。
- 读取失败、解密失败、版本不支持和恢复失败必须保留明确错误状态。
- 保留现有加密恢复日志及写入门禁。
- 不在日志、源码和测试夹具中写入真实 API Key、密码或私人聊天内容。
- 测试使用合成数据。
- 不得声称未执行的测试已经通过。
