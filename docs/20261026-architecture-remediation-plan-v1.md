# 架构问题修复与分阶段验收计划

日期：2026-10-26（北京时间）。状态：规划完成，业务实现尚未开始。

用户目标：修复本轮架构检查发现的问题，先规划分阶段验收。依据为 [架构检查](20261026-architecture-extensibility-review-v1.md)、[验证基线](qa/architecture-20261026/verification-summary.json)、实际源码与现有测试。本计划是过程文档，不是已经通过的修复验收。

## 目标与约束

保留 Vue 3 + Pinia + Capacitor 技术栈，按“数据保护 → 备份恢复 → 模块接入 → 业务契约 → 边界治理 → 整体验收”推进。每阶段完成后记录结果和遗留项；阻塞验收的问题在本阶段解决，不混入下一阶段的大范围改造。

兼容约束：现有业务存储键、记录 ID、历史日期与重复规则不变；完整备份 v1–v12 继续可导入，旧版本缺失字段沿用当前兼容语义；两种入口验证模式、敏感数据按需解密、后台释放、改密回滚及 API Key 安全保存继续有效。新增内部恢复日志独立版本化，不因此无条件升级完整备份格式。

本轮不新增用户可见业务，不加入云同步，不默认迁移数据库，不整体替换路由库；新增接口为消除当前耦合服务。性能测量后若发现数据库迁移确有必要，另列数据迁移方案，避免与安全修复混在一起。

仅用合成记录、测试凭据和隔离设备环境验证。不读取私人备份，不在日志或夹具保存真实密码/API Key。已有审查材料与用户文件保留。

## 阶段 1：普通业务存储故障保护

### 修改范围

首批修复 `scheduleStore`、`weightStore`，并核查、补齐 `debtStore`、`moodStore` 的同类加载与写入保护。新增小型可复用状态/持久化辅助层，保留各模块业务规则；Todo、聊天和 API Key 先适配一致的外部错误含义，保留已有并发与安全能力。

1. 区分 `idle/loading/ready/error` 与保存状态；`isDataLoaded` 仅表达成功加载。只有存储明确返回不存在时允许初始化，解析错误、驱动异常和未知版本不能等价于空数据。
2. 加载分两步：读取并验证必要字段，全部成功后提交内存状态。加载期间禁止 watcher、自动补齐、迁移写回和普通业务修改；多键读取中一项失败也不能提交半套默认值。
3. 页面提供加载失败提示和重试入口，阻止未加载数据的新增、删除、排序和导入；Store 动作本身也要保护。首页、报表、提醒、桌面组件不得把失败模块当空数据继续生成覆盖结果。
4. 保存串行处理，保留最新待保存内容；失败状态可见并可重试。`flush()` 对未完成保存和失败结果负责，不能仅等待一个吞掉错误的队列就宣称保存成功。
5. 加载重试不得覆盖更新的内存修改；写失败后的重试保持最新输入，防止迟到写入把新内容覆盖。若尚未落盘就被系统强杀，不能承诺恢复内存草稿，页面须明确保存状态。

### 验收标准

| 场景 | 必须验证的结果 |
| --- | --- |
| 有旧记录，读取抛错，后续写入可用 | 不写空、不允许普通修改；存储原值保持不变；新建 Store 后可读回原记录 |
| 读取成功但 JSON 损坏、类型异常或不支持的版本 | 报错并保留原值，不自动“修复”为空集合 |
| 省钱/心情多键加载只有一个键失败 | 不写回部分默认值，不运行补齐或迁移，保留所有原键 |
| 明确无历史记录 | 正常初始化和新增，保存后重新创建 Store 可恢复 |
| 保存失败、连续编辑、稍后重试 | 错误可见，最新内容保留并正确保存，无重复记录、无迟到覆盖 |
| 切后台执行 flush | 有失败就反馈失败，不能显示“已保存”；通知/桌面快照不发布失败状态的空数据 |
| 点击页面重试 | 实际 Store 重新加载并恢复操作能力，不能只消除提示 |

使用实际 Store、真实 watcher 和组件动作测试，仅在存储驱动处注入故障。原两项问题转为常规安全回归；补齐省钱、心情和相关页面。阶段结束运行 `npm run check`，记录新增用例及检查结果。

## 阶段 2：完整备份恢复与中断恢复

### 修改范围

从 `useBackupSettings` 提取实际恢复协调器，UI 负责选文件、认证和反馈，协调器管理准备、写入、提交、回滚与恢复。这里的“事务”是带恢复记录的应用级协调，不宣称底层多种存储具有同一个原子事务。

1. 恢复前等待相关模块加载及待写队列结算，校验整个输入；校验失败零写入。阻止恢复期间的普通修改、自动保存、后台同步和改密并发。
2. 在修改业务键之前，安全保存并校验恢复所需的旧快照和进度；敏感快照须加密，包含的 AI 配置同样受保护。恢复日志无法持久化或读回验证失败时，不开始覆盖业务数据。
3. 明确恢复策略：提交标记前中断，重启后回滚至原快照；提交标记完成后保留目标快照，重试通知/桌面刷新及日志清理。过程必须幂等，重复启动恢复不会重复导入。
4. 应用启动先探测未完成恢复，在业务 Store 可写之前设置恢复门禁；需要解密时先验证身份。关闭全屏入口验证也不能绕过未完成恢复的写入保护。
5. 任一模块失败时等待所有已发起写入结算，再执行补偿；回滚失败明确上报恢复状态，暂停受影响写入，保留恢复材料和重试入口。
6. 提交成功后才刷新派生提醒和桌面快照；派生刷新失败显示可重试的同步状态，不重复导入业务记录。

### 验收标准

- 测试直接调用产品使用的协调器及实际 Store，不另写一套模拟事务作为验收替身。
- 导入非法数据零写入；任一业务写入失败可回滚；延迟写入不会在回滚后再次破坏数据；回滚持续失败时显示恢复提示并阻止普通写入。
- 在日志准备后、每个业务参与者写入后、提交前后、清理时分别模拟进程重启，重新实例化运行时读取同一合成持久化数据。结果只允许完整旧快照、完整新快照，或明确禁止使用的待恢复状态，不能让混合状态进入普通编辑。
- 日志损坏、密钥不可用、恢复材料写失败均有保留与阻断策略；不泄露明文。恢复材料验证时检查实际持久化内容，不只检查内存。
- v1–v12 各版本通过与其实际格式对应的夹具验证；缺失 Todo 的旧备份保持既有语义；省钱分组、心情定义、密码分类、聊天、AI 配置、壁纸和安全开关完整往返。
- 保留已有 API Key、可选解锁、聊天恢复和改密故障回归，`npm run check` 通过。

阶段 2 的进程中断单元测试先验证协调策略，原生强停/冷启动的真实持久化验证纳入阶段 6；两种证据分别记录。

## 阶段 3：模块清单与生命周期

### 修改范围

建立应用层模块清单，集中 ID、标题、菜单图标、异步页面、设置能力、安全属性及缓存策略；路由校验、菜单、标题、设置入口从同一清单派生。配置描述不直接导入所有业务 Store，保持敏感模块懒加载。

模块生命周期采用明确的 `initialize/resume/flush/dispose` 等接口，按实际需要提供；应用控制器管理平台事件、认证流程和调用顺序，业务模块管理自身加载、订阅、定时器与通知刷新。导航状态从混合 Settings Store 提取，现有调用可通过薄兼容层逐步迁移。

### 验收标准

- 所有现有页面入口、标题、模块设置、深链参数、返回栈、滚动恢复、未读提示及温馨小家开关保持一致。
- 两种入口验证模式下，受保护页面和缓存均遵守现有会话规则，进入普通页面不额外解密聊天或密码库。
- 启动、恢复前台、切后台、卸载/重新挂载后，没有重复通知调度、重复订阅或遗留监听/定时器。
- 在测试组合根增加一个普通合成模块，仅提供模块描述和生命周期并注册，验证能进入、显示标题、返回及 flush；无需修改 App 和控制器的模块条件分支。生产配置不包含该测试模块。
- 重复模块 ID、无效设置目标等配置在启动检查或测试中明确失败；`npm run check` 通过。

## 阶段 4：备份和敏感模块契约

### 修改范围

普通业务模块提供备份参与者接口：`export/validate/restore/flush` 及必要元数据；敏感业务额外提供 `load/release/reencrypt`。由应用组合根注册能力，备份协调器和受保护会话从能力集合调用，清除固定两种敏感模块的分支和重复名单。

格式兼容层继续负责历史 v1–v12 结构到模块数据的转换，不能把历史业务语义全部塞入通用注册器。阶段 2 的恢复、保护和日志行为原样迁移，设置 UI 仅选择备份范围和显示结果。

### 验收标准

- 第三种合成敏感参与者注册后，自动参与认证后加载、后台释放、改密、完整备份及恢复，生产产品不增加测试入口。
- 在每个改密参与者处注入失败，所有已开始的参与者均被正确反向回滚；回滚失败进入恢复保护。操作租约覆盖进行中的写入，失效后不保留明文会话。
- 单模块备份只请求必要能力；完整备份遗漏参与者、未加载参与者或格式未知时明确拒绝，不以空数据代替。
- 导出的既有备份结构和字段兼容；阶段 2 所有故障和重启回归继续通过，`npm run check` 通过。

分成可独立回退的小步执行，每步只扩展对应测试，整阶段结束做完整检查。

| 子步骤 | 实施内容 | 验收重点 |
| --- | --- | --- |
| 5A 仓库边界 | 将体重、日程、心情、省钱的直接存储操作逐步收敛到可注入仓库；沿用原键和格式 | 同一仓库契约套件在内存驱动和实际平台适配器上验证；Store 不直接依赖插件；阶段 1 的故障保护有效 |
| 5B 公共领域逻辑 | 日期工具从日程领域提取；整理心情回音壁与聊天共享提示能力；跨模块生活上下文由应用层组合 | 跨月/闰年/本地日期/重复锚点结果不变；Todo 领域不再借用日程业务文件，无新增依赖环 |

| 5E AI 与文档 | AI 请求层接收显式运行参数，应用适配器提供设置与凭据；更新 README 的路径、安全模式、模块接入及备份约定 | 现有请求协议、流式/回退/取消/错误分类保持；驱动测试无需实例化全局 Settings Store；不新增真实服务商请求 |

新增 lint 导入限制只约束明确的分层边界，既有必要应用层聚合采用显式白名单，不“一刀切”禁止所有特性协作。源码正则测试中限制重构的部分改为实际行为测试，必要的原生资源约束保留。

阶段结束：`npm run check` 通过；本阶段触及的 lint 警告消除，总警告不高于基线 55；现有业务数据往返、阶段 1–4 的故障用例持续通过。

## 阶段 6：Android、CI 与整体交付验收

### 自动化与原生规则

- 为 JS Todo 领域和 Java `TodoRepository` 使用同一套合成 JSON 规则夹具，覆盖一次性、每天、每周、自定义间隔、跨月/闰日、历史保护、单次覆盖与完成状态；分别执行双方实现并比较结果。
- CI 增加 Android 测试执行，不能只 assemble。纯 JVM 可验证的规则放入单元测试；依赖 Android Context/SharedPreferences 的测试在隔离模拟器运行 instrumentation，不强行归为无 Android 依赖的单元测试。
- 保留 Web 的 lint、领域/组件、类型和构建门禁；将新故障、安全和契约测试纳入常规命令。原审查探针保留为历史证据，不加入“期望不安全行为”的常规门禁。
- 原生依赖补丁仍需幂等及源码不匹配失败检查。构建使用当前依赖锁文件，不顺带升级依赖。

### 实际用户流程

在独立测试应用数据或临时模拟器用户中验证：两种入口验证、日程/体重/省钱/心情增删改、失败提示与重试、聊天与密码库按需访问、后台锁定释放、API Key 冷启动保持、主密码变更、完整/单项备份导出解密与导入、Todo 桌面勾选、提醒与深链返回。

实际强停并冷启动验证阶段 2 的未提交恢复回滚及已提交恢复保留。测试必须经过产品实际协调器，测试驱动不得自行实现一套事务来代替产品行为；正式 APK 不包含故障注入钩子。

### 性能与交付

1. 使用明确记录规模的合成数据测量启动、单条保存、导出导入及内存表现，规模至少覆盖小集合与万条历史记录；测试记录设备、WebView、数据组成及耗时。模块拆分前保存同环境基准。
2. 以固定环境三次运行的中位数比较关键路径；若耗时或内存相对基准恶化超过预设 20% 调查线，定位原因后复测。该数值是计划采用的回归调查线，不是当前已测性能或所有设备的体验承诺。数据保护所需的安全写入成本单独说明，不静默放宽结论。
3. 必需检查全部通过，未通过、未运行或受环境阻塞的项目单独列出。模拟器不可用时允许记录代码阶段完成，但不能将原生验收标成通过。
4. 提供每阶段变更、验证命令、实际结果、证据路径和回退说明；最终完成需要 Android 原生测试与恢复流程证据。若交付可安装包，按日期/阶段命名新 APK 放入 `output/`，保留旧包并记录摘要；只有通过对应验收的包可标为已验收。
