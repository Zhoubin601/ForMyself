# 架构扩展性检查

日期：2026-10-26。基线：`ceda70f1e14e288c7b697b0e7123d6deee9cb895`。本轮为检查与建议，未修改业务代码，未执行提交或推送。

## 结论

当前架构适合个人应用持续迭代，模块内加字段、调整规则、扩充界面较方便；新增完整业务模块、接入新的敏感数据类型或更换数据存储时，公共代码的改动面仍然较大。可以继续沿用 Vue + Pinia + Capacitor 的模块化单体，但应先统一存储失败保护，再收敛模块接入点和备份协议，无需整体重写。

本轮额外复现了两处读取失败后的覆盖风险。它们比目录整理更应优先处理，也说明已有测试全部通过不能代表存储故障路径安全。

## 发现与优先级

### P1：普通模块未统一“读取失败后禁止写回”

**日程：已复现。** `features/schedule/scheduleStore.js:56` 读取或解析抛错后仅记录日志，`finally` 仍设置 `isDataLoaded = true` 并调用 `persist()`，将初始空列表写回同一个业务键。只要读取暂时失败而后续写入可用，旧日程就可能被覆盖。

**体重：已复现。** `stores/weight.js:10` 读取失败后同样标记已加载，用户新增记录会触发 `deep watch`，以仅包含新记录的列表覆盖旧存储。它不会像日程一样立即写空，但继续编辑会带来覆盖风险。

证据：[故障探针](qa/architecture-20261026/storage-faults.spec.js) 使用实际两个 Store，仅替换存储驱动，并预置合成旧数据后注入一次读取异常；两项均观察到旧内容被替换。结果见 [JSON](qa/architecture-20261026/storage-faults-results.json)。探针通过表示问题已复现，不表示功能安全或问题已修复；未在真实设备注入故障。

建议先建立统一的 `idle/loading/ready/error` 状态，只有成功读取或明确确认无数据后才允许持久化；读取失败保留原文件，提供重试，写失败保留待保存内容并反馈。API Key 与 Todo 的失败处理可作为现有参考，但应统一接口而非复制实现。

### P2：模块接入点分散，应用编排承担过多业务细节

可定位的接入点：

| 接入职责 | 当前实现 |
| --- | --- |
| 页面导入、图标与渲染 | `App.vue:9`、`:286` 附近的条件分支 |
| 菜单、模块设置入口 | `composables/useAppController.js:86` |
| 路由白名单、设置范围 | `services/navigationHistory.js:1` |
| 页面标题与模块设置白名单 | `stores/settings.js:226`、`:454` |
| 启动加载、订阅、切后台保存 | `composables/useAppController.js:366`、`:399` |
| 备份序列化及恢复分派 | `services/fullBackup.js:77`、`composables/settings/useBackupSettings.js:50` |

例如增加一个带设置和备份的“习惯”模块，除新建业务文件外，还要同步上述公共接入点；有深链、首页卡片、提醒或敏感数据时继续增加改动。漏改一处可能表现为入口存在却无法导航，或数据没有进入完整备份。

`useAppController.js` 有 572 行，集中身份验证、平台事件、业务启动、通知、桌面快照及生命周期编排；`settings.js` 有 595 行，同时管理导航、主题、安全、AI 和健康配置，容易成为新增功能的集中修改点。

建议先以一个明确的模块清单集中 `id/title/view/settings/access/cache` 元数据，导航和菜单从清单派生；将启动、恢复、后台保存拆成显式的业务生命周期接口，由应用层组合。是否引入 Vue Router 应取决于后续路由复杂度，单独换路由库不会消除这些分散接入点。

### P2：完整备份与安全模块协议仍依赖固定名单

`services/fullBackup.js:1` 直接导入多个业务的规范化函数；`useBackupSettings.js:66`、`:127`、`:149` 手工列举每种数据的获取、恢复和副作用。加入模块必须同步维护协议、选项和恢复逻辑。

完整恢复通过 `Promise.allSettled` 写入所有模块，失败后用内存中的旧快照再次恢复（`:149–176`）。这是进程内补偿，未见持久化的跨模块恢复日志；进程在部分写入后结束时，不能据此保证整套数据一致。回滚失败只记录日志，没有将 `rollbackFailed` 传递到受保护会话的恢复保护机制。这一项为源码审查结论，本轮未执行完整恢复强停或回滚失败实验。

此外，`stores/protectedAccess.js:9`、`:58`、`:108`、`:145` 和 `useSecuritySettings.js:49` 固定处理密码库、聊天两种模块。加入第三个加密模块必须同时改加载、释放、改密参与者和备份认证名单，不能只在界面添加验证入口。

建议定义各模块的 `export/validate/restore/flush` 备份接口，以及敏感模块的 `load/release/reencrypt` 接口。应用层仍明确管理整体事务顺序；先补回滚失败可见状态与写入保护，再按需求引入加密恢复日志和启动恢复。注册接口时必须保留 v1–v12 备份兼容和当前敏感数据释放规则，避免纯机械拆分。

### P2：存储适配统一，但数据仓库与规模策略尚未统一

体重、心情、日程等 Store 仍直接序列化整个集合并调用 Preferences。当前数据量下便于实现；随着记录增长，单条更新会产生整集合序列化和写入，查询与启动加载也依赖内存全量数据。本轮没有大数据压测，不判断已出现性能瓶颈。

Todo 已具备可注入仓库、revision 冲突处理、原生与 Web 驱动（`features/todo/todoRepository.js:7`），可以先推广这类仓库边界；小配置继续保留 Preferences，大记录集合是否迁移 IndexedDB/SQLite，应由容量与查询测量决定。

Android Todo 在 `TodoRepository.java:50` 等位置实现重复规则与日期推导，JS 也维护规则。扩展重复类型时要保证双方一致。CI 当前只构建 Android debug APK，没有运行原生单元或仪器测试（`.github/workflows/quality.yml:20`）。建议共享合成规则夹具，分别验证 JS 和 Java 输出，不把桥接可编译当成规则一致性验证。

### P3：目录分层和类型边界仍偏弱

- 省钱、体重、密码库等仍分布在 `components/stores/services`；其余模块已迁往 `features`。建议随改动迁移，避免一次性纯路径重排。
- `features/todo/todoCore.js:1` 从日程业务借用日期函数；心情视图引用聊天提示词，聊天提示词又引用心情领域函数。当前没有文件级 import 环，但特性之间的边界较松。共享日期放入明确公共领域工具，跨模块生活上下文在应用层组合，不应把所有逻辑都塞进共享目录。
- `SettingsView.vue:24–35` 通过展开所有设置 composable 创建一个大 `context` 并传给子组件。字段重名和接口漂移难以发现；可按设置分区提供明确的 props 和动作。
- `tsconfig.json:7` 明确关闭 `checkJs`，也未启用 `strict`；当前类型检查不能视为全部业务 JS 契约已受保护。应先对模块描述、仓库、备份格式及跨层 DTO 增加 JSDoc/TS 类型，再逐步收紧。
- 一部分测试用源码正则断言布局、函数名或代码片段，如 `tests/unlockPerformance.test.js`，结构调整容易引起无行为变化的失败，且不能替代故障测试。保留必要资源约束，新增规则优先验证可观察行为；lint 可加入明确的跨模块 import 限制。
- README 仍展示旧心情模块路径，并描述强制入口验证；与实际 features 路径及可选入口验证不一致，需要更新模块接入与存储约定。

## 按扩展场景判断

| 扩展场景 | 当前便利程度 | 主要原因 |
| --- | --- | --- |
| 现有模块加字段、规则或界面 | 较好 | 已有独立领域函数和测试，仍需同步备份与原生规则 |
| 新增普通业务模块 | 一般 | 接入导航、启动、设置、备份要改多处公共代码 |
| 新增加密业务模块 | 较弱 | 加载、释放、改密及备份参与者固定为两种模块 |
| 接入兼容 chat/completions 的 AI 服务 | 较好 | URL、模型可配置，统一请求封装 |
| 接入不同 AI 协议或更换持久化引擎 | 一般偏弱 | AI 引擎直接读取 Settings Store；多数业务 Store 直接调用 Preferences |
| 扩大历史记录量或支持多端同步 | 需先设计 | 当前以本机全量集合和局部 revision 为主，未提供跨设备冲突协议 |

## 建议顺序与完成标准

1. **先保护存量数据。** 修正日程和体重的加载失败写回，统一加载/保存错误状态；将本轮复现改为“故障后原数据保持不变”的正式回归。补充恢复与回滚失败保护。
2. **集中模块接入点。** 先用现有一个普通模块验证清单与生命周期接口；目标是后续普通模块接入不再修改应用控制器中的业务分支。
3. **建立备份与敏感模块契约。** 保持历史格式兼容，验证第三个合成参与者的加载、释放、改密回滚和备份，避免名单遗漏。
4. **再逐步加强仓库、类型和原生契约测试。** 由实际数据量决定数据库迁移，随功能开发拆分 `ChatView.vue`（1,731 行）、`HomeView.vue`（1,141 行）等职责集中的文件；不要只以行数作为重构目标。

以上为建议，具体功能路线和改造取舍尚未由用户确认，本轮不实施重构、不生成正式发布包。
