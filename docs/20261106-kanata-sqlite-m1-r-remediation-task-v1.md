## 2. 六项专项审计与修复

每项统一执行：**真实现状 → 风险/失败复现 → 根因 → 最小修改 → 正负例/故障测试 → 验证证据 → 结果 PASS / NOT-A-DEFECT / BLOCKED**。发现不属于 M1 的业务命令，不提前做 M2/M3；只修复能在 M1 Schema/升级器边界内确认的缺陷，并记录后续阶段责任。

### R1｜schema_migrations 真实执行时间

当前 Schema 定义中 `schema_migrations` 记录版本、名称和 checksum；迁移器在事务中写入日志。检查是否需要补充准确的 `applied_at`（或等效执行时间）以满足审计和恢复追踪，以及时间由哪个层生成。

**验收要求：**
- 对每次**成功提交**的版本升级保留真实的应用时间，明确 UTC/时区、单位及精度；失败与回滚不能出现伪成功的 applied_at。
- 如果需要失败尝试历史，必须与“成功应用记录”区别对待，不得把回滚后不存在的尝试伪装成已应用版本。
- 处理连续升级、重试、进程中断、跨时区和数据库时钟差异；不以构建时间、文件创建时间或启动时间代替实际应用时间。
- **兼容现有 001/002 校验和及已生成数据库。** 先研究升级器对 sqlite_schema、日志 checksum 的严格验证。若增列/新表需要版本迁移，按追加版本的安全策略设计和测试；不能直接改写已应用的历史迁移而导致旧库被拒。若现有语义足够，说明依据，不增加冗余结构。

### R2｜character_instances.location 及空值语义

当前 `character_instances.location` 为 `TEXT NOT NULL`；需结合真实领域类型与校验器确认 `''` 是否是合法的“暂无地点”。同时审视 `virtual_schedules.location`、事件动作位置等字段，但不要把所有 location 混为同一种语义。

**验收要求：**
- 分别验证 `''`、`NULL`、字段缺失、普通字符串和边界值；保留业务要求的 NULL / 空字符串区别。
- 合法的 `''` 不应被 `trim` 非空校验误杀；如果业务明确要求非空，应给出领域契约和旧数据依据。
- 不使用虚构地点作为默认值；不通过删光 NOT NULL/CHECK 来掩盖兼容问题。
- 测试直接 SQL、合成记录投影和重复运行；不得提前实现 M5 生产旧数据导入器。

### R3｜消息 revision 与历史快照的可追溯性

当前 `messages.revision` 和 `message_audits` 相关表、触发器已存在；**实际编辑/删除的 CAS、审计与 stale/needsReview 原子命令按原计划属于 M2/M3**。本轮检查的是 M1 结构是否有能力正确保存既有历史及拒绝结构性非法引用。

**验收要求：**
- 对照类型/校验器确认每条历史快照关联的 `world_id`、`conversation_id`、`message_id`、previous/next revision、时间、发言者和内容是否可正确表达。
- 用合成 SQL 验证连续修订链、错误 revision、错世界/会话、错误发言者、未来 revision、删除标记及重复审计的结构行为。
- 明确“当前消息值”与“先前版本快照”不同；禁止因编辑而覆写原快照。若旧资料未保留旧版本，不能凭空生成其历史。
- 区分 Schema 能保证的约束与需在 M2/M3 的原子事务命令里保证的行为，不为通过测试提前大改 Repository、Pinia 或 UI。
- 若确有 Schema 约束缺陷，附最小复现、修复和回归；否则记录 NOT-A-DEFECT 及交接到 M2/M3 的精确条款。

### R4｜审计记录不可变、顺序与事务一致性

检查 `message_audits`、`event_audits` 的触发器、外键、快照约束、重复记录和事务行为。先区分消息修订、事件审计、Schema 升级日志及后续 M5 数据迁移 journal。

**验收要求：**
- 明确已提交审计事件能否被普通 UPDATE / DELETE 直接篡改；若需要数据库层保护，应设计防修改/防误删测试，不能只在 JS 中约束。
- 验证当前 schema 支持明确的 revision 顺序、不可重复的关键事件与对应消息/事件的归属一致性；不能把缺号自动填成虚假的历史事件。
- 对提交、回滚、重试与崩溃检查审计和关联业务数据是否原子；仅属于 M2/M3 的命令级原子写入要列入后续验收，不提前声称已实现。
- 不为“连续性”无依据地引入哈希链；已有完整性/加密机制不能被 SHA checksum 冒充。
- 补充正向、直接非法修改、重复、错世界、回滚及重启负向测试。

### R5｜逐字段映射与信息保真说明

M1 v1 报告已有“当前集合/字段 → SQL 表”的领域级映射，但尚应核对能否对**每个重要字段**清楚说明新列、JSON 扩展、缺失/NULL、转换及验证责任。

**特别边界：** 当前 Schema SQL 版本为 001/002（目标 version 2）；KanataData 的 1/2、全备 v13、未来 M5 的旧 JSON/归档导入是不同概念。**不得把“M1 schema 迁移”误写成“v4 → v5 已实现数据迁移”。M5 才实现旧数据导入。**

输出逐字段映射文档，至少包含：

| 旧实体/字段 | 旧类型及可选性 | SQL 目标表/列 | 表达方式（列/JSON/关系表/不直接迁移） | NULL/缺失/默认 | 校验与转换 | 保真限制 | 测试或源码证据 |
| --- | --- | --- | --- | --- | --- | --- | --- |

重点核对世界、角色卡/版本/实例、默认世界与身份、会话/参与者、消息/sender/revision、世界书、记忆/来源、事件/effects/因果撤销、角色关系、权限、后台任务、水位、统计与扩展字段。对 `messageArchives` 只做未来 M5 展开需求和映射规则，不伪造当前已导入；旧 `virtualEvents` 只能标记旧摘要，不得伪造原消息引用。未知扩展字段、字段不存在与显式 NULL/false/空数组的区分必须说明。默认世界/实例/私聊会话的建立属于相应数据初始化/导入流程，不可仅凭 Schema 假设已完成。

本轮交付的是**字段级映射审计和 M5 接口/验收准备**，不是生产旧数据迁移器。

### R6｜外键 ON DELETE、保留历史与引用语义

从实际 `PRAGMA foreign_key_list`、Schema 目录和运行时事务检查所有关键关系（世界→实例/会话，成员→消息，会话→消息，消息→审计/记忆来源/事件来源，事件→effects/审计，迁移日志等）。

**验收要求：**
- 逐条输出父表、子表、复合键、当前 `ON DELETE`（SQLite 默认 NO ACTION 不等于自动级联）、建议语义、领域理由及验证用例。
- 区分物理删除、软删除、归档、撤销、逻辑解绑。不得为了删除方便而 CASCADE 清掉 revision、来源或审计，也不得无依据地把全部删除一律禁止。
- 对父项仍被引用、非法悬挂引用、跨世界关联、回滚、延迟 FK、重复迁移进行真实数据库测试。
- 保留 `PRAGMA foreign_keys=ON` 与 `PRAGMA foreign_key_check`；不能关闭外键、改成无约束 JSON 或使用 OR REPLACE/IGNORE 绕过。
- 如需改变删除策略，先说明是否会破坏现有数据/审计，兼容已存在版本再实施追加迁移；若实际 Schema 符合预期，记录无须改动的证据。

## 4. 实施与回归流程

### 阶段 A：基线与逐项复现

1. 获取当前 M HEAD、工作区状态、实际 Schema 版本/DDL checksum。
2. 运行已存在的 M1 定向测试，记录真实命令、环境及结果。
3. 对 R1–R6 形成“现状证据 / 可复现缺陷 / 不属于当前阶段 / 待确认”的矩阵。**不得因为本清单列出六项就预先认定六项全失败。**

### 阶段 B：小步修复

1. 对已证实的每项 M1 缺陷给出根因及最小实现。
2. 新测试应能在修复前失败、修复后通过，至少包括正常、非法、边界、事务失败及可安全重试情形。
3. 对历史 001/002 的 Schema/日志 checksum 和严格比对逻辑，先设计向前兼容；必要时追加 migration，不静默重写既有已用版本。
4. 复测空库逐版升级、已有 v1/v2 升级、未知未来版本拒写、损坏/陌生数据库拒写、失败回滚、重启重试、重复执行幂等。
5. 检查审计来源和跨世界复合外键，不允许为修一项破坏另一项。

### 阶段 C：完整回归与 Android 边界

按仓库实际可执行脚本开展：

- `tests/kanataSqliteSchema.test.js` 及新增 R1–R6 测试；`npm run check`；类型正负样例。
- M1 原有真实 SQLite / 主机 SQLCipher 测试、故障注入（包括 SIGKILL，至少覆盖与新增改动相关的写入点）、安全拒绝路径。
- 按现有 M1 QA 指南，在**独立合成 AVD**上重新核对相同 DDL、约束、FK、回滚和重启；只有实际跑到的检查才标 PASS。若无设备/SDK/磁盘条件，明确写 BLOCKED / NOT RUN，不冒用原报告结果。
- 在适用测试连接执行 `PRAGMA foreign_keys=ON`、`PRAGMA foreign_key_check`、`PRAGMA integrity_check`，SQLCipher 环境再按现有工具执行密文完整性检查。
- 只将 Android 原生 DDL 测试称为原生 DDL 测试；**不冒充 JS migration 与生产 Driver 端到端测试**，后两者按 M2/后续阶段门禁验证。
- 如果补丁没有触及设备行为且无需重跑设备，说明范围、复用的历史证据及不足；不能把未重跑写成“本次通过”。

记录实际测试命令、退出码、运行平台、SQLite/SQLCipher 版本、数据指纹、代码/设备 APK 指纹及保存位置。保留失败前后的真实证据。不要宣称未实跑的 1k/10k/100k 性能已达到 M7/P7 门槛（Android 512 MiB、完整改密 120 秒、Web 768 MiB 原门槛仍然有效）。

### 阶段 D：两轮独立自查

**第一轮：** 事务原子性、旧库兼容、外键/审计不可变性、空值和 revision 反例、故障恢复、权限/密钥泄漏边界。

**第二轮：** 对照 M1 的五个正式门禁、当前领域类型/校验器、M0/M1 真实证据、M2–M7 责任、README/AGENTS 链接与文档结论；确认没有改动 `raw/`、`Kanata`、`main`、生产 UI/Store。

发现确凿问题就修复并重测，直到没有未经记录的失败；无法验证就标记阻塞，绝不伪造 PASS。
