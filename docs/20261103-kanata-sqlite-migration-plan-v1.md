## 1. 目标与非目标

### 目标

1. Android 上 Kanata 的聊天消息、会话、世界、角色实例、记忆、事件、关系、任务和使用统计由 SQLite 持久化。
2. 对话历史使用基于复合索引的游标分页；读取最近消息不需要加载全部历史。
3. 单条消息新增、修订、删除和状态更新只触及相关记录，不再为了小改动序列化完整 KanataData。
4. Pinia 只持有当前世界、当前会话、当前角色与有限消息窗口；不再长期持有十万条消息组成的完整数据对象图。
5. 使用事务保证消息、会话状态、使用统计及记忆/事件来源关系的一致性。
6. 保留世界隔离、角色知识边界、记忆来源 revision、事件因果撤销、权限 read/remember/share 和受保护会话机制。
7. 迁移过程可中断续接、可校验、可回滚；旧数据只在明确验收和后续用户确认后清理。
8. 以 1k / 10k / 100k 合成数据进行可重复性能测试，并保留实测命令、设备、数据集指纹和原始结果。

### 非目标

- 不重写 ForMyself 全部业务模块。
- 不在本阶段把 Web 强制迁移到 SQLite WASM/OPFS。
- 不因为数据库迁移而删除原有 P7 容量、安全、备份或需求验收门槛。
- 不将数据库文件直接当作跨平台备份格式。
- 不在 UI、Pinia 或组件内直接执行原生数据库调用。
- 不以牺牲来源追溯、权限校验、事务完整性或加密强度换取性能数字。
- 不迁移旧「温馨小家」聊天业务数据；旧 JSON 的兼容读取仅服务于 Kanata 当前数据格式与已批准的备份恢复范围，不改变此前“不迁入旧小家聊天”的产品决定。

## 2. 当前架构问题与迁移必要性

当前 Kanata 的主要存储路径仍包含完整数据对象序列化和文件级加密：

**KanataData → assert/normalize → JSON.stringify → AES → 文件写入**

历史消息虽已使用独立加密归档页（每页最多 50 条），但主数据仓库和 Store 仍存在完整 KanataData 读取、校验、复制与持久化路径。仅把底层文件换成 SQLite，而继续在 Store 中持有完整消息数组，不能解决主要内存问题。

因此 M 必须同时完成：

1. **存储引擎迁移：** Android 文件型 JSON/AES 存储 → SQLite/SQLCipher。
2. **访问模型迁移：** 全量对象快照 → 按需 Repository 查询、游标分页、局部写入。
3. **生命周期迁移：** 页面/会话关闭、锁屏、改密、恢复时释放连接、缓存和明文引用。
4. **备份迁移：** 由数据库导出生成分块备份，而不是重新拼成一个巨型 JSON。

若只完成第 1 项，M 不得验收通过。

## 3. 目标架构

- Vue Views
  - Pinia：只管理当前页面状态与有限消息窗口
    - Domain Services
      - Kanata Repository Contracts
        - AndroidSqliteDriver：SQLite + SQLCipher，通过 Capacitor 原生插件
        - WebFileDriver：M 阶段保留现有 Web 加密文件/归档实现
      - Backup / Restore Coordinator：统一管理便携加密分块备份

### 分层约束

- 领域服务依赖 Repository 接口，不依赖 Capacitor 插件。
- Android Driver 封装数据库连接、事务、参数绑定、分页、批量写入、迁移和关闭。
- Web Driver 保持现有加密文件实现，提供相同业务语义；平台差异在应用组合根注入，不允许业务层判断平台后散落 SQL/文件分支。
- Repository 不返回长期存活的完整数据库快照；默认返回有界 DTO。
- 需要批量处理的数据通过异步分批读取/写入，不允许先 materialize 全表。
- 所有 SQL 使用参数绑定；禁止字符串拼接用户输入构造 SQL。
- 数据库连接、事务和明文结果必须遵守 protected session / operation lease / restore gate 生命周期。

## 4. Android 数据库与加密方案

### 候选技术

首选验证对象为 @capacitor-community/sqlite（与 Capacitor 8.3.1 的准确版本和 peerDependencies 以 M0 安装验证为准）。SQLCipher 作为 Android 数据库加密候选。不得在 M0 前将未经验证的插件版本写入 lockfile 或生产依赖。

M0 必须核对：
- Capacitor 8.3.1、Android Gradle/JDK 21 与插件版本兼容。
- SQLCipher 在目标 Android 构建变体中真实启用，而非误用明文 SQLite。
- 插件连接、关闭、事务、批量执行、并发、升级和错误语义。
- 加密密钥是否会被插件写入普通 Preferences、日志或其他明文持久化位置。
- 插件许可证、SQLCipher 许可证/声明、依赖体积与发布合规。
- Android 目标设备上 100k 数据的实际 RSS、查询延迟、写入延迟和改密成本。

如果候选插件不能满足密钥生命周期或性能要求，M0 必须比较自建最小 Capacitor Native Plugin 的成本；不能为了“用了插件”而接受不安全密钥管理。

### 密钥生命周期

- 不得把明文主密码或 SQLCipher 密钥写入普通 Preferences、日志、文件名或测试报告。
- 数据库解锁只在受保护会话有效时进行；锁屏、会话释放、应用退出和恢复失败时关闭连接并清除可释放的明文缓存。
- 优先采用随机数据库密钥（至少 256 bit）与版本化密钥封装：数据库密钥由主密码派生的独立 KEK 包装，封装记录保存 KDF 算法、参数、salt、nonce、版本和认证标签；数据库密钥只在解锁会话内存中短暂存在。
- KDF 方案及参数必须在 M0 根据现有密码策略、可用原生实现和实测耗时确定；不得直接复用旧 CryptoJS/OpenSSL Salted/EVP-MD5 派生值作为 SQLCipher 原始密钥。
- Android Keystore 可用于设备绑定的辅助密钥保护，但不得成为跨设备备份恢复的唯一密钥来源；备份必须能由用户主密码在另一台兼容设备恢复。
- 如果插件的密钥 API 会自动将明文 secret 持久化到普通偏好存储，必须禁用该路径或改用受控原生桥接。
- 所有密钥轮换必须有 journal、阶段状态、故障注入和回滚验证。

### 主密码修改语义

- M 不得改变 ForMyself 全局主密码的产品语义或绕过 protectedModules 的协调流程。
- Kanata 数据库密钥封装可以随主密码变化重新包装；是否需要 SQLCipher rekey 由密钥架构决定并由 M0/M6 实测。
- 全局主密码修改仍须处理其他受保护模块、备份和恢复参与者；不能只因 Kanata envelope 更新成功就宣称全局改密完成。
- 必须测试改密中断、重启、旧密码拒绝、新密码成功、旧密钥/封装退休和恢复 journal 一致性。

## 5. 数据模型与索引基线

M1 以当前 kanataTypes.d.ts、领域校验器和真实业务引用为准，建立版本化 Schema。以下为逻辑表清单，不是允许 Agent 脱离源码直接照抄的最终 DDL。

| 领域 | 建议表 | 关键要求 |
|---|---|---|
| 世界 | worlds | 稳定 ID、版本、状态 |
| 角色卡 | character_cards, card_versions | 原始卡与世界实例经历分离，保留未知扩展字段 |
| 世界身份 | world_identities | 每个世界独立用户身份 |
| 角色实例 | character_instances | world_id 约束、实例状态与关系独立 |
| 会话 | conversations, conversation_participants | 私聊/群聊、成员唯一性、世界归属 |
| 消息 | messages | 稳定 ID、revision、sender snapshot、reply 引用、状态、时间 |
| 世界书 | lorebook_entries | 激活规则、优先级、预算、可见范围 |
| 记忆 | memories, memory_sources | 分层、冲突状态、来源 message_id + revision |
| 关系 | relationships | 有向关系、世界/角色实例作用域 |
| 事件 | world_events, world_effects, event_sources | 因果链、撤销/重建、来源追溯 |
| 自主生活 | background_tasks, virtual_schedules | 去重键、水位、调度状态 |
| 权限 | life_grants | world + instance + module + read/remember/share |
| 使用统计 | usage_events | attempt 唯一性、真实/估算/缺失来源、价格版本 |
| 审计 | event_audits, message_audits | 修订历史与可追溯性 |
| 迁移 | schema_migrations, data_migrations | Schema 版本、导入游标、数据指纹 |

### 消息查询

- 消息主查询必须使用 (world_id, conversation_id, created_at, id) 组合索引。
- 最近消息使用 ORDER BY created_at DESC, id DESC LIMIT ?。
- 历史翻页使用 keyset/cursor pagination，不使用大 OFFSET。
- 对消息正文搜索先实现索引化的元数据过滤；FTS5 作为可选后续能力，必须验证中文分词/查询语义与索引更新一致性后再启用。
- 所有消息关联都校验 world_id；优先通过复合外键/唯一约束在数据库层防止跨世界引用。
- 消息编辑/删除必须递增 revision 或按现有领域规则写入审计；记忆/事件引用旧 revision 时标记 stale/needsReview，不能静默改指向新内容。

### JSON 的保留边界

SQLite 不意味着禁止 JSON。角色卡原始 payload、未知扩展字段、灵活配置和低频读取的结构化快照可保存在 TEXT JSON 列中。高频过滤、排序、关联、权限检查和分页字段必须规范化为独立列并建立索引。

## 6. M0–M7 阶段与验收门禁

每个阶段必须：核对真实源码 → 小步实现 → 定向/负向/故障测试 → 两轮独立自查 → 复测 → 记录证据 → PASS 才进入下一阶段。不得把计划文档或编译成功当成阶段实现。

### M0：技术验证与基准冻结

**目标：** 先证明候选 SQLite/SQLCipher 方案能在当前 Android 项目安全运行，并且在目标设备上有性能收益。

工作：
1. 读取 AGENTS、架构规范、当前 Kanata 源码、package/lock、Android 构建配置和现有受保护会话/改密流程。
2. 建立独立 prototype 或隔离测试模块，不替换生产 Repository。
3. 验证插件与 Capacitor 8.3.1 兼容、SQLCipher 真加密、密钥不落明文、连接关闭、事务、批量写入、错误恢复。
4. 用合成 1k/10k/100k 消息数据测插入、最近 50 条查询、游标翻页、单条更新、批量导入、数据库打开/关闭、冷启动和内存峰值。
5. 同一设备/同一数据集对照当前 JSON/归档实现，记录 P50/P95、RSS、CPU、数据库体积和操作耗时。
6. 确定插件准确版本、密钥封装方案、WAL/同步配置、批量大小和可量化的 Android 性能目标。

**必须验收：**
- Android Debug/QA 构建成功，插件 API 与当前 Capacitor 版本真实运行。
- SQLCipher 加密数据库不能被普通 SQLite 以明文方式读取；错误密钥不能打开。
- 主密码/数据库密钥不出现在普通 Preferences、日志、测试输出。
- 插入、查询、更新、事务回滚、进程强停后完整性检查全部通过。
- 100k 最近 50 条查询与历史翻页不会将全量消息载入 JS。
- 对比基线给出真实数字和设备信息；若无真实目标手机，模拟器结果只能作为初步证据，M0 标记设备性能门禁 BLOCKED。
- M0 冻结性能目标和依赖版本；达不到收益或安全条件时停止并重新评估，不继续 M1。

### M1：Schema、约束和版本迁移

**目标：** 建立可演进、可校验的数据库结构。

**必须验收：**
- 所有表、主键、唯一约束、外键、索引、NOT NULL/状态约束与领域模型映射明确。
- 复合约束能阻止跨世界会话成员、消息、关系、记忆来源和事件来源引用。
- Schema migration 可从空库逐版升级；失败事务回滚，重启可安全重试。
- 未知未来 schema 版本拒绝写入并给出可恢复错误。
- 合成非法记录、重复 ID、孤儿引用和 revision 冲突测试通过。

### M2：消息与会话 Repository

**目标：** 先迁移最影响性能的消息路径。

**必须验收：**
- 新消息单条/批量写入不重写全部历史。
- 最近消息、向前分页、跳转原消息、引用回复、编辑、删除、重试、状态和群聊成员语义保持。
- 同时间戳排序稳定；cursor 绑定 world_id/conversation_id，不能跨会话复用。
- 页面只保留有界消息窗口；快速切换世界/会话时过期请求不能写错目标。
- 并发写入、重复请求、事务失败和进程中断测试通过。
- 当前 UI、群聊 speaker、消息气泡与 AI 上下文的行为回归通过。

### M3：世界、角色、记忆、事件与自治 Repository

**目标：** 将 Kanata 其余结构化业务数据迁移到 SQLite。

**必须验收：**
- 世界、角色卡版本、实例、世界书、关系、事件、effects、任务、授权和统计均可持久化与查询。
- 记忆来源保留 message_id + revision；原文归档后仍能按需解析来源。
- 事件撤销只回滚其自身 effects，不覆盖无关事件。
- read/remember/share 三权限在查询上下文之前执行；撤权后禁止新读取与分享。
- 自治水位只在事务成功提交后前进；重复任务不会重复写事件。
- 关键跨表写入具备事务一致性和幂等键。

### M4：Pinia 与业务访问模型重构

**目标：** 移除完整 KanataData 常驻内存和全量复制路径。

**必须验收：**
- Store 不再持有全量 messages/archive pages；只持有当前活动范围和有界缓存。
- Repository API 提供分页、计数、按 ID/条件查询、事务命令和批量迭代器。
- 业务组件不直接导入 SQLite 插件；平台差异只存在于组合根/Driver。
- 旧 update(data => ...) 全量快照模式被逐步替换为明确的领域命令，禁止把整库查询后再传回 Store。
- 页面销毁、锁屏、受保护会话释放后关闭连接并释放明文缓存。
- 运行时与测试证明普通聊天写入不会触发全量 JSON.stringify 或全量消息克隆。

### M5：旧 JSON/归档数据迁移器

**目标：** 将当前 Kanata JSON 主数据与加密历史归档导入 SQLite。

**必须验收：**
- 只读取 Kanata 当前批准的数据范围；不导入旧「温馨小家」聊天、记忆、事件和关系。
- 每批读取/解密/校验/写入；批次大小可配置并有内存上限。
- migration journal 记录源指纹、目标 schema 版本、表、cursor、已导入数量和状态。
- 重复执行幂等；中断后从已提交批次续接；批次事务失败不产生半批数据。
- 对比 worlds/cards/instances/conversations/messages/memories/relationships/events/permissions 等各表数量、稳定 ID、revision、来源引用和关键字段哈希。
- 迁移完成前旧文件只读保留；迁移失败不得初始化空世界或删除源文件。
- 迁移后抽样回读和全量计数/哈希核对通过，才允许标记完成。

### M6：加密备份、恢复、改密与故障恢复

**目标：** 使 SQLite 不破坏现有全局安全架构。

**必须验收：**
- 定义版本化便携备份格式（建议 V3），分块导出/加密/校验，不把十万条消息重新拼成单个巨大 JSON。
- 备份包含 schema version、数据集指纹、记录计数、分块哈希、KDF 元数据和认证信息；不得包含明文密码/密钥。
- 恢复按批导入临时数据库，完整性校验通过后由现有 restoreCoordinator 统一切换。
- 保留 v1–v12 完整备份的既有兼容要求，旧 chat 清理/过滤决策不变。
- 全局主密码改密通过 protectedModules/reencrypt 协调；不能只轮换 Kanata 就宣称全局成功。
- 强制停止、磁盘空间不足、错误密钥、损坏分块、恢复日志损坏、数据库连接中断等故障注入均有明确安全结果。
- 改密后新密码成功、旧密码失败；失败回滚后原数据仍可用。
- Android 数据库备份/恢复不得依赖复制一个处于 WAL 活跃状态的裸数据库文件；必须使用受控 checkpoint/SQLite backup API 或事务一致的导出方案。

### M7：性能验收、文档收口与合并准备

**目标：** 证明新架构达到性能目标并可安全交回 Kanata。

**必须验收：**
- 1k/10k/100k 合成数据完整回归；关键读写、分页、索引、备份、恢复、改密记录 P50/P95、RSS、CPU、磁盘体积。
- Android 使用同一目标设备/固定模拟器配置、同一数据集指纹、同一构建候选；结果可复现。
- 保留原 P7 Android 512 MiB 与完整改密 120 秒门槛，不得调高；若测量定义需修订，必须给出证据并单独审批，不能在 M 中自行更改。
- Web 仍使用辅助存储适配器并保持功能；Web 旧 P7 768 MiB 门槛不因 Android 迁移而自动豁免。Web 未通过时标记 P7 仍 No-Go。
- 全部 M 测试、npm run check、Android 原生测试、迁移/备份故障测试通过。
- 文档、README、架构规范、版本记录和验收摘要同步。
- 输出 M0–M7 验收矩阵、测试证据、未解决风险和合并说明。
- M 通过后仅准备合并回 Kanata；未经用户明确授权不得合并 main、发布正式 APK 或删除真实旧数据。

## 7. 性能测试规范

- 数据全部使用可复现合成数据；记录生成器版本、随机种子、数据集指纹、消息分布、正文长度分布和世界/会话数量。
- 测试设备记录型号、Android 版本、RAM、CPU、存储介质、构建类型、电源/温度状态。
- 至少覆盖 1k / 10k / 100k 消息；若设备允许，增加 500k 作为扩展观察，不以扩展档替代 100k 门禁。
- 查询测试包括最近 50 条、向前翻页 50 条、按 ID 跳转、会话计数、世界隔离过滤和记忆来源回查。
- 写入测试包括单条消息、连续流式分段写入、群聊多角色一轮、批量导入、编辑/删除与事件事务。
- 记录 P50/P95、峰值 RSS、CPU 时间、GC/分配概况、数据库文件大小和 WAL 大小。
- 冷启动与热启动分开；每个性能场景至少重复 5 次，报告中给出中位数和 P95。
- 不得强制 GC、降低完整性验证、跳过加密或用 UI 首屏显示代替数据库分页证明。
- 任何比较必须在相同设备、相同数据集、相同构建模式下进行。

## 8. 分支与 Git 操作规则

1. M 分支从 Kanata 的 73158a058d35124e1572b2161fe0f364f2140c48 创建；当前 M 计划提交后，以实际最新 M HEAD 作为 M0 开发基线。
2. M 阶段所有 SQLite 迁移代码和 M 文档只提交到 M；不在 Kanata 并行改相同存储模块。
3. M 允许普通阶段检查点提交；不得 reset --hard、clean、强制推送、覆盖用户未提交改动或擅自删除文件。
4. 不把 M 合并到 main。M 完成并通过 M7 后，先审查 M 与 Kanata 的差异、冲突、测试证据和备份协议，再经用户明确授权合并回 Kanata。
5. 合并回 Kanata 后，更新 P7 的基线 SHA 和测试证据；旧 P7 的失败结果保留为历史，不得冒充新架构测试。
6. 合并后继续 P7 原始验收：Android 512 MiB、Android 完整改密 120 秒、Web 768 MiB 及完整需求场景。SQLite 迁移成功不等于 P7 自动通过。
7. 在 M 未完成前，P7 仅暂停在 Kanata 分支；M 不得擅自删减 P7 的原始需求、验收项或门槛。
