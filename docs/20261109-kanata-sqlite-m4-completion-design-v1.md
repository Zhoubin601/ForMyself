# Kanata SQLite M4 Completion 设计增量

C2 首先隔离来源验证与正文读取。消息来源链仅投影 ID、revision、归属、状态与规范化授权。SQLite 递归去重负责访问范围，JS 通过固定页消费授权。发现旧版本、缺失节点、异会话或无终点的链时拒绝。单来源读取不需将整个关联图交给 Vue。保留旧的单条返回接口和授权语义，固定查询进入现有 catalog。

管理读取按单条详情和有界关联拆分。提交命令继续在候选保护队列内复核 scope/owner、revision 和恢复门禁。事件预览需冻结集合、处理决定与 revision；事件变更、审计和 Effects 重放同事务。全局角色绑定单独使用全局 owner，旧世界 owner 不得授权其写入。

## 群聊成员变更

产品已确认方案 1。候选成员编辑命令在现有受保护会话、恢复门禁和 Conversation Repository 事务内复核当前世界、会话类型、revision 与消息是否存在。存在性查询只读当前会话的消息元数据，不能以可见聊天窗口为空作为依据。归档或软删除后仍保留的历史消息也计入。若确认期间出现首条消息，提交不能继续走原地更新分支，应让用户重新确认创建新群。

- 尚无消息时，原地按新名单更新成员，保留 conversation ID。
- 已有消息时，界面提示会保留原群并另建新群。确认后用独立 conversation ID 和新成员名单在当前世界建群。原群记录、成员集合、消息和历史引用均保留，原成员继续通过原群按现行规则访问历史。
- 新群从空消息窗口开始。近期消息、历史检索、锚点、引用和角色上下文继续绑定当前 conversation ID，新成员通过新群无法读取原群历史。候选成员校验沿用当前世界角色限制，异世界成员拒绝整次提交。

候选成员编辑的验收入口和负例见 [访问矩阵](20261109-kanata-sqlite-m4-completion-preflight-v1.md#访问矩阵补齐项) 与 [群聊成员变更验收用例](qa/kanata-sqlite-m4/completion/README.md#群聊成员变更验收用例)。本设计沿用已有历史权限与引用作用域。

## 当前实现差异

- 共享记忆链使用 SQL 递归去重，按消息、事件和授权关系分批消费。角色归属与共享链状态先于正文。候选单条详情仅取正文投影；来源页和原文解析分别绑定记忆、角色、世界与源 revision。旧 `readFor` 及写入兼容路径仍可能积累来源 DTO，不能把本轮深链证据扩展为全部宽关系通过。
- 事件因果浏览按前因或后续返回最多 50 项，游标绑定世界、根事件、方向和根 revision。它是实时浏览，不是撤销确认令牌。原批量预览、Effects 重放和审计事务保持原入口，尚需有界化及接入候选管理 UI。
- 世界身份、独立建群、世界书编辑、角色卡库、记忆详情和全局生活角色绑定接入原工作区。单一详情/草稿从当前页加载。卡列表、版本标题、角色和因果关系每页 50。卡片原始导入 payload 只进当前导入候选，不进入全局卡列表。原生文件选择实际切后台后的导入续接未验证。全局绑定选择与世界 owner 分开，修改通过 CAS 并撤销旧候选会话，生活模块消费仍待接入。
- 候选已有独立建群。空群原地编辑和由历史群成员编辑触发的确认、分流与回归仍待接入。
